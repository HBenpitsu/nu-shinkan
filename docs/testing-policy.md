# テスト方針

この文書は、リポジトリのテストで何を検証し、何を検証対象から外すかを定める。独自の振る舞いを直接検証し、テストの保守負担と実行環境への依存を抑えることを目的とする。現状の実装やテストを説明するものではなく、実装が従うべき方針を示す。

## 検証対象の判断

テストが必要な複雑さを持つ対象を検証する。期待結果は業務ルールから定め、正常系だけでなく境界条件や不正な入力も扱う。

以下は複雑な対象や境界条件の例である．

| 検証する対象 | 検証する振る舞いの例 |
| --- | --- |
| グラフ探索 | 到達性、循環、空集合の扱い |
| 設定の更新 | 指定値の反映、削除、未指定値やコメントの保持 |
| 対象の選択 | 選択条件、空の指定、未知の対象の拒否 |
| 独自のバリデーション | 設定構造や名前の業務上の制約、不正入力の拒否 |

次の処理はテストしない。

- 標準ライブラリのパーサや直列化など、標準機能そのものの挙動。
- stdin・stdout・stderr、終了コード、単純なI/Oや保存呼び出し。
- 引数転送、単純な委譲、プロパティの転記。
- ループ構造・ネストされた分岐構造を持たない15行以下の関数。

行数やループの存在だけでテストの必要性は決まらない。単純関数の除外条件に当たらなくても、単なる委譲・標準処理ならテストしない。たとえば、設定の更新・保存を呼ぶだけの関数ではなく、設定側の更新・削除規則を検証する。

## テストの設計

検証対象のロジックに取得済みの値を渡し、結果や状態の変化を直接確認する。標準機能の呼び出し方や実装の手順をなぞるだけの検証は作らない。

一時ファイルは、設定の更新・削除・コメント保持などの意味的な検証に使う。標準I/Oの動作確認を目的にしない。外部サービスをモックする場合も、検証対象は独自の再試行規則などの振る舞いとする。モックしたこと自体は、対象外の処理をテストする根拠にならない。

テストのためだけに単純な処理を公開・抽出したり、依存注入や実行器を追加したりしない。別ファイルへの移動や行数の増加によって検証価値が生まれるわけではない。内部関数の公開が必要な場合は、[testExportsの作例](./snippets/ts_export_for_test.md)を参照する。

## テスト中のCLIツール呼び出し禁止

CLIはコマンドラインから起動するプログラムを指す。[CLIの作成方針](./make-cli.md)に基づいて分離されたエントリーポイントは、テストしない、テストからimportしない。

タイムアウトが頻発してフリーキーなテストになるのを避けるため，テスト中にCLIツールを呼び出さない。ヘルパー、モック内の実装読み込み、内部関数を経由した間接的な起動も禁止する。テストでは、エントリーポイントの外にある検証価値のあるロジックを直接呼び出す。

ここで禁止するのはテスト処理によるCLIツールの呼び出しであり、テストランナー自体の起動や本番処理でのCLI実行は対象に含まない。

## GitHub Workflowと診断ログ

GitHub Workflowはテストしない。YAMLの文字列検証、シェル・Actionの代替実行、コマンドの組み立て、通知・集計の再現などによる代替テストも作らない。

Workflowの品質改善ではロギングを充実させる。まず、処理の段階、対象、終了状態、失敗理由をログから判断できるか確認し、不足する情報を追加する。対象が空の理由や結果集計に必要な情報の欠落などを記録する。

環境変数値、トークン、設定ファイル内容はログに出さない。機械可読な出力に診断文を混ぜない。ログは実行後の原因調査に使うものであり、事前の自動回帰検出を代替保証しない。

## 検証結果と保証の範囲

実装・テストを変更した場合は、対象のテストと必要な型チェック・ビルドを実行する。安定性を評価するときはキャッシュの再利用と実行結果を区別し、結果・所要時間を記録する。測定せずに不安定性が解消したと断定しない。

テストを整理するときも本番仕様を維持し、残る検証と自動検証しなくなる範囲を明示する。内部ロジックの検証だけで、入出力や外部ツールとの連携まで保証したと扱わない。

文書のみの変更では、リンク先、Markdown構造、作例と方針の整合を確認する。文書変更のためのテストは追加しない。

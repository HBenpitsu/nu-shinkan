# このドキュメントの目的

このドキュメントでは，[メンタルモデル](./deploy-model.md)を前提として，実装方針を整理していきます．なお，現状との比較や，現状との比較によって明らかになった実装に必要なステップなどについては，[実装作業書](./deploy-impl.md)に譲ります．

# トリガーフェーズ

channel と，変更検出の比較基準・対象となるコミットの SHA を組で記録し，後続フェーズへ受け渡します．

トリガーフェーズは，GitHub Actions の Workflowで実現されます．

## update モード（staging / release）

`update` モードのデプロイは，channel に対応するタグの付け替えによって起動します．`staging` channel は `staging` タグ，`release` channel は `release` タグに対応します．

通常の起動では，タグの付け替え前のコミットを変更検出の比較基準，付け替え先のコミットを変更検出・デプロイの対象とします．

### フォールバック系

デプロイ失敗や再デプロイが必要な際には，`workflow_dispatch` によってfull modeデプロイを発火します．対象は指定した channel に対応するタグが指すコミットに限定し，要求受付時にその SHA を記録します．任意のコミットを直接指定することはできません．

### 要求の干渉

デプロイの進行中にタグやブランチが更新され，ふたたびデプロイがトリガーされることを要求の干渉といいます．
なお，コミットSHAを記録してデプロイを進めるため，干渉が起こっても進行中のデプロイが使用するコミットは変化しません．

`update` modeでは，同じ channel の要求について，タグ更新順の変更を漏れなく反映し，処理完了後の環境が最新のタグ更新に対応する状態になることを保証します．古い要求の反映によって新しい状態を上書きしてはいけません．手動の full デプロイも同じ制御の対象とします．

全フェーズを直列実行することまでは要求しません．要求をまとめる場合も，途中の要求が担う変更を取りこぼさないことが必要です．要求の順序管理，反映の排他制御および集約の具体的な方式は実装作業書で定めます．

### 運用上の注意

通常経路の比較基準は前回のタグ位置であり，前回デプロイに成功したコミットではありません．そのため，デプロイ失敗後にそのままタグを更新しても，未反映の変更が次の差分に含まれるとは限りません．失敗後は，対象 channel のタグが指すコミットを full デプロイして復旧してから，通常のタグ更新を再開します．

### 補足

- `release` タグの付け替えは，本番反映の決定を表す操作として扱います．CI/CD はこの操作によって release の起動条件が満たされたと判断します．タグを動かす前の認証・承認や，候補の確認を行うフローは，このドキュメントのスコープ外です．
- タグを更新する Workflow は，GitHub App のインストールアクセストークンを使用してタグを push します．`GITHUB_TOKEN` による push では後続の Workflow が起動しないため，GitHub App を用いてタグ更新からデプロイへの連鎖を成立させます．詳細は [GitHub のトークン仕様](https://docs.github.com/en/actions/concepts/security/github_token)を参照してください．

## review モード（preview）

`review` モードのデプロイ（`preview` channel）は，mainブランチに対するPR のOpen（`opened`, `reopened`）と head ブランチの更新（`synchronize`）によって起動します．変更検出の比較基準には起動時の PR の base コミット（mainのhead），変更検出・デプロイの対象には PR の head コミットを使用します．レビュー用環境の識別情報として，PR 番号も次のフェーズへ受け渡します．

### フォールバック系

デプロイが失敗したり，デプロイしてほしい対象が拾い漏れた場合は，PRへの`/preview <package-name> ...`の書式のスラッシュコマンドでデプロイを発火します．
(`<package-name>`は基本`@repo/xxxx`の形式です)

コマンド受付時に対象 PR の head SHA を取得して固定し，パッケージの実在性確認からデプロイまで，同じ SHA を使用します．引数が空の場合はワークフローを異常終了し，Usage として `/preview <package-name> ...` を案内します．

### 要求の干渉

同じ PR に新しいデプロイ要求が発生した場合，古い要求をキャンセルして新しい要求を処理します．これはGithub Actions workflowの`concurrency`フィールドの設定で実現できます．

# 計画フェーズ

計画フェーズでは，トリガーから受け取った要求をもとに，デプロイ候補のパッケージ・接続構成を具体化します．通常経路では変更検知を用い，フォールバック経路では全対象の列挙または手動指定によって対象を選びます．

計画フェーズは，GitHub Actions の Workflow から `turbo` コマンドや補助スクリプト（`turbo`の実行結果の解析など）を呼び出して実現します．

`turbo`による差分検出を行う通常経路では，計画フェーズで`fetch-depth: 0`の checkout を行います．変更検知を行わない full・manual-pick では，対象コミットのみを取得します．

計画フェーズの出力はActionsの GITHUB_OUTPUT に書き込み，後続フェーズに受け渡します．後続フェーズも基本的にはWorkflowであるため，（channelやPR番号など）トリガーフェーズの出力を再出力するようなことはせず，トリガーフェーズの出力値が必要な場合は直接利用させます．

計画フェーズの出力は次の書式の表現したjsonデータです．

```jsonc
{
    "changes": [ // for ci
        {
            "package": package名,
            "path": packageへのパス
        }
    ],
    "targets": [ // for cd
        {
            "package": package名,
            "path": packageへのパス
        }
    ]
}
```

`changes`はテスト対象，`targets`はデプロイ候補を表します．review モードでは connection グラフによる選定を行うため，`changes`が`targets`のサブセットになるとは限りません．

ここで選ばれるパッケージは，変更や依存関係などに基づいて選ばれたパッケージで，`package.json` に `scripts.deploy`を持たないパッケージ（デプロイ不能パッケージ）も含まれることがあります．ただし，これは実行フェーズでスキップすればよいだけなので，計画フェーズでは特に対処を行いません．

`targets`が空の場合も，`changes`があれば準備フェーズでテストを実行します．デプロイ用アーティファクトの生成とデプロイは行いません．テストが成功した場合は通常経路では正常終了します．ただし，manual-pick ではデプロイできる対象がなかったものとして異常終了し，その旨をPRにコメントします．

## update モード（staging / release）

### デプロイ対象の選定

`changes`は，`turbo ls --filter=[BASE...HEAD]`によって取得した変更があったパッケージを含みます．デプロイ時には統合テストを行わないため，直接変更のあったパッケージのテストで十分です．

`targets`は，`turbo ls --filter=...[BASE...HEAD]`によって取得した変更の影響があることが検知されたすべてのパッケージを含みます．

差分を検出できない場合は，同じ対象 SHA の full デプロイへフォールバックします．タグ初回作成などで比較基準がない場合や，比較処理が失敗した場合に加え，巻き戻しや分岐をまたぐタグ移動により `[BASE...HEAD]` では移動前後の変更を正しく捉えられない場合も含みます．正常に比較できた結果が空である場合は，検出失敗とは区別します．

### 接続構成

各パッケージと環境変数配布基盤（env-config）で，`release` profile または `staging` profile 向けに設定された接続構成をそのまま採用します．計画フェーズで接続先を個別に組み替える必要はありません．

### フォールバック（full）

変更検知を行わず，対象のコミットにあるすべてのワークスペースパッケージを候補とします．この全候補を`changes`と`targets`の双方に設定し，全候補をテスト対象とします．接続構成は通常経路と同じです．

## review モード（preview）

### デプロイ対象の選定

`changes`は，`turbo ls --filter=[BASE...HEAD]`によって取得した，変更があったパッケージを含みます．

`targets`は，`turbo ls --filter=...[BASE...HEAD]`によって取得した，変更の影響があることが検知されたすべてのパッケージ（被変更パッケージ）を起点として，各プロジェクトが`deployment.yaml`で張るconnectionグラフを元に計算します．

（ここで，BASEは前回previewデプロイを行ったコミットではなく，PRのBASEであることに注意してください．）

`targets`の計算前に，`deployment.yaml`の`connections`フィールドの設定値からconnectionグラフを作ります．connectionグラフは，`deployment.yaml`を配置したパッケージが子ノード, `connections`フィールドに設定されたパッケージが親ノードとなる有向グラフです．探索用の辺は親（接続先）から子（接続元）へ向けます．自己ループと，実在しないパッケージへの接続は，辺がないものとして扱います．循環の存在を前提とし，探索が停止するアルゴリズムを用います．
`targets`は，”被変更パッケージからreviewEntry=trueであるパッケージへのパス”のすべてを考え，それらに含まれるパッケージを集めて計算します．起点自身が`reviewEntry=true`の場合は，長さ0のパスとしてそのパッケージも含めます．

### 接続構成

`staging` profile を基礎に，`targets`内のWorkerリソースと，`targets`外の既存リソースへの接続を区別します．

`targets`内への接続（URL/ServiceBinding）の場合，これを`preview`用接続（URL/サービス名）に差し替えます．
`targets`外への接続の場合，`staging` profileの設定値を維持します．

`preview`用接続では，Workerの名称として素の名称に`-preview-pr-{PR_NUMBER}`サフィックスを追加したものを用います．また，urlとしては，`[Worker名]-preview-pr-{PR_NUMBER}.nushinkan2.workers.dev`を用います．

なお，計画フェーズではこの意思決定がコードやデータとして現れない可能性があります．

### フォールバック（manual-pick）

`/preview <package-name> ...` の引数から，手動指定されたパッケージのグループを取得します．変更検知は行わず，指定されたパッケージの実在性を確認します．
実在しないパッケージが存在する場合は，ワークフローを異常終了し，その旨をスラッシュコマンドへの返信コメントとして通知します．このとき，"MAYBE: `/preview 実在したパッケージのみの列`"などのコマンド例を含みDXに配慮します．
また，DXの観点から，この種の異常終了はワークフローのトリガーから，理想的には10秒以内，少なくとも20秒以内に完了する必要があります．（pnpm installに--filterオプションを入れるなど，ワークフローを工夫する必要があります）

正常系では，コマンドに指定された起点のパッケージを`changes`に設定し，テスト対象とします．`targets`は，まず指定した起点を含め，パッケージ依存関係による影響先へ展開し，その結果を起点として通常経路と同じ方法で connection グラフ上の対象を収集します．接続構成も通常経路と同じ規則で決定します．

# 準備フェーズ

次の順で処理します．

1. テスト・ビルド・env-config の実行に必要な`devDependencies`も含めて依存解決: `pnpm install`
2. `@repo/env-config`を実行可能な状態に整え，環境変数を`sync`: `pnpm sync`
3. テスト実行
4. デプロイアーティファクトの用意

3以降については，Workflowとして直接これらの作業をするのではなく，`turbo run`を介して各プロジェクトに依頼する形を取ります．

テストは`turbo run test`に`--filter`オプションで`changes`のパッケージを指定して実行します．
テストが失敗した場合，ワークフロー全体を異常終了し，その旨を通知します．(preview channelの場合はコメントを書き込みます)

デプロイアーティファクトとは，`.generated/.env.deploy`, `.generated/wrangler.jsonc`および，frontendプロジェクトではビルドアーティファクト`./dist`です．
デプロイアーティファクトの用意は，`turbo run build`に`--filter`オプションで`targets`を実行し，各プロジェクトの`build`スクリプトを発火させるという形で行います．

Workflowから`build`スクリプトには，環境変数を介してDEPLOY_CHANNEL, PR_NUMBER(preview channel以外では -1), targetsが供給されます．
`build`スクリプトをローカルで使用する際，デプロイ用の入力が提供されない場合は，local環境でのbuildであると判定します．デプロイ Workflow では必要な入力を供給し，デプロイ用のアーティファクト生成時に不足していれば異常終了します．

デプロイ用のアーティファクト生成では，DEPLOY_CHANNEL が未指定または未知の値の場合は異常終了します．preview では PR_NUMBER を正の整数として要求します．preview 以外では PR_NUMBER が供給されても使用しません．接続構成の生成に必要な targets など，必要な入力・設定が揃わない場合も異常終了します．

ビルドアーティファクトの生成方法は明らかなのでここでは説明せず，`.generated/`配下の`@repo/env-config/materialize`によるデプロイアーティファクトの生成に関して以下に説明します．

全対象の準備が成功してから実行フェーズへ進みます．アーティファクトの用意で異常終了した場合も，ワークフロー全体を異常終了し，その旨を通知します．(preview channelの場合はコメントを書き込みます)

## update モード（staging / release）

[configuration-design](./configuration-design.md)の仕様にしたがってプロジェクト直下に
`.generated/.env.deploy`, `.generated/wrangler.jsonc`を生成します．

## review モード（preview）

updateモードと同様の処理の後，計画フェーズの意思決定に基づいた変更を加えます．

また，`preview`接続を成立させるため，`wrangler.jsonc`の`name`フィールドを`-preview-pr-{PR_NUMBER}`を付した形に変更し，`routes`フィールドを削除してカスタムドメインを無効化します．

※カスタムドメインを使用しないため，workerから別のworkerへの直接のfetchは失敗します．service bindingに置き換えてください．

# 実行フェーズ

計画フェーズから受け取った候補のうち，対象コミットの `package.json` に `scripts.deploy` が定義されているパッケージをデプロイします．定義されていないパッケージはデプロイをスキップします．この規則は通常経路・full・manual-pick に共通です．

`turbo run deploy`に`--filter`オプションで`targets`を渡せば，`deploy`スクリプトの有るパッケージのみデプロイを発火できるはずです．
通知フェーズ用に，このコマンドの標準出力は次に送ります．

fullmodeでは，対象コミットの全ワークスペースパッケージのうち，deploy スクリプトを持つものすべてに対して，デプロイを再実行します．過去の実行結果による省略が行われないように注意してください．

各対象は並列数の上限の範囲でデプロイし，一部が失敗しても残りを続行します．一つでも異常終了したデプロイがあった場合，workflow全体は異常終了します．ただし，review modeでは通知フェーズをスキップしないように注意してください．

`targets`内に実行可能な deploy タスクが一つもない場合，基本的には正常終了します．ただし，manual-pickでは異常終了し，deployできる対象がなかったことをPRにコメントします．

# 通知フェーズ

## update mode

通知対象がないため，このフェーズで明示的にすることはありません．
各フェーズでのロギングを怠らず，後にGithub Actionの結果を見たときに状況をつかめるようにしておきます．

## review mode

標準出力から取得した実行フェーズの実行結果を解析して，
対象のPRにコメントとして，次を通知します．

対象となったすべてのパッケージについて
- パッケージ名
- デプロイ済み/デプロイ不要/デプロイ失敗
- (存在すれば) ワーカー名
- (存在すれば) frontendパッケージの場合，アクセス用のURL
- (デプロイ失敗の場合) エラーメッセージ
